# Hybrid SDD

The founder's standing method for ALL software development, in every project and session
(founder rule, 2026-10-23). It is project-agnostic: apply it to every software project (new or existing,
any stack), not only Chartivia; Chartivia was merely the first adopter. Project-specific values live only
in each repo's `.sdd/config.json`. Opus (architect, medium reasoning) writes only documents; Gemini 3.8
Flash High (ultra reasoning) writes tests, code and reviews in separate one-shot processes; zero-token
scripts decide pass/fail. Role isolation is absolute: Opus never writes product code or bypasses gates;
when the user asks, verify and report current worktree phase, gate state, and role boundary evidence.
Canonical repo: https://github.com/98H/hybrid-sdd (METHOD.md is normative;
local clone /root/hybrid-sdd).

## When to Use
- Any request to build, change, fix or retrofit software in any repo (new feature, bug with a
  contract change, refactor, new product).
- Don't use for: one-off scripts, ops/sysadmin tasks, research answers, config tweaks with no product code.

## Prerequisites
- Repo has Spec Kit (`.specify/`) — else install: `uvx --from git+https://github.com/github/spec-kit.git specify init --here --force --non-interactive --ignore-agent-tools --integration claude --script sh`.
- Hybrid SDD files in the repo: `scripts/sdd/` (canonical repo `scripts/*` + `prompts/` → `scripts/sdd/prompts/`) and `.sdd/config.json` (from `templates/sdd.config.json`, adapted: build/test/regression, failureMarkers, acceptanceDir, protected, highRisk, uiProbe).
- Hermes config (applied on this host 2026-10-23, backup config.yaml.bak-20261023-sdd): `delegation.model=ag/gemini-3.8-flash-high`, `delegation.base_url=http://localhost:20128/v1`, `delegation.reasoning_effort=ultra`, `agent.reasoning_overrides.cc/claude-opus-5-5=medium`.
- Implementer command (verified working): `hermes chat --oneshot --yolo -Q -m ag/gemini-3.8-flash-high --reasoning ultra --query-file {PROMPT_FILE}`.

## Time optimisation (founder rule 2026-10-31: fastest wall-clock possible without more tokens and without hurting quality or cost)
Normative text: canonical repo METHOD.md §11. The code is in the repo's `gates.mjs` and `run_phase.sh`, proven by `tests/selftest_speed.sh`. Keep each project's `scripts/sdd/` synced with the canonical repo (`cp /root/hybrid-sdd/scripts/{gates.mjs,run_phase.sh} scripts/sdd/`).
- **Gates (automatic):**
  - Fail fast: lock/scope FAIL skips everything after it, and build FAIL skips the rest.
  - Regression runs only when every earlier gate passed.
  - Acceptance lanes: set `acceptanceParallel` and `acceptanceLanes` in `.sdd/config.json` per repo. Put files that share a rate limit, port range, upstream session or the served app's mutable state in ONE lane. Size by CPU/RAM (browser test ≈ 250 MB). Use `{LANE}` in `acceptanceRun` for per-lane locks.
  - The reviewer starts when all pre-regression gates pass (`SDD_PRE_PASS_HOOK`) and overlaps regression. PASS still needs both.
  - The verdict has per-gate `sec` and `totalSec`. Tune lanes from them.
- **Architect (me):**
  - Never idle. While the implementer or the gates run, review the next area against real sources, write the next FR and test draft, and lock them only after the current phase merges.
  - Report and start the next step in the SAME turn. Never park work "for tomorrow" when today's data already allows the check.
  - Before locking a caching, de-dup, rate-limit or timing FR, grep locked tests that count upstream calls or inject consecutive faults, and amend them in the same commit.
  - When an escalation was caused by a test, re-gate the existing code before a new implementer run.
  - Sandbox red-checks of tests that spawn other tests.
- **Never trade quality or cost for time:** no fewer attempts, no lower reasoning, no skipping the reviewer or regression, no gates against production, and no parallel implementer sessions for tasks that share files.

## Procedure
1. **Constitution (once per repo).** Ensure `.specify/memory/constitution.md` contains the *Hybrid SDD* principle from the repo's `templates/constitution.md`. Done when present and founder-approved.
2. **Specify (architect = me, Opus).** From the founder's 1-2 line intent run the full chain `speckit-specify → speckit-clarify (if ambiguous) → speckit-plan → speckit-checklist (high-risk features) → speckit-tasks → speckit-analyze`, then write `specs/NNN-x/review-checklist.md`. Every requirement is `FR-xxx` and machine-checkable; spec has SC-xxx; every task cites exact paths and `(FR-xxx)` or is tagged `(infra)`; phases ≤ 8 tasks. Mapping to every Spec Kit command: repo SPEC-KIT-PARITY.md. After hotfixes run `speckit-converge`. Done when `node scripts/sdd/verify_specs.mjs --spec specs/NNN-x --pre-tests` exits 0.
3. **Approval (new feature intent only).** Send the founder ≤10 lines (stories, risks, phase/task count, files, ≤3 questions). Wait for approval once per new feature. Never ask approval for follow-up phases: converge and fix phases from your own reviews, next-defect phases, or deploys. Find the defect, write FR + locked test, run the phase, review, deploy, then report. Never end a report with "shall I start?" or "with your approval…"; start the next phase before writing the report.
4. **Acceptance tests (Gemini, separate process).** `terminal(command="bash scripts/sdd/author_tests.sh specs/NNN-x", background=true, notify=true)` (`--retrofit` for existing behaviour). Done when the log ends with `AUTHOR OK`.
   - **Pre-flight lint of the locked tests (zero tokens, before phase 1).** Grep `tests/acceptance/NNN/` for hidden environment assumptions and amend them on the base branch now. Each one otherwise costs a whole escalation round later:
     - Localized strings asserted with no `switchLanguage(...)` / settings-key setup before them (the test assumes a default language).
     - Blanket "zero console errors" filters on a path where the contract REQUIRES an HTTP error. Chromium logs every 4xx/5xx as `Failed to load resource`.
     - Imports of helper exports that `tests/qa_lib.cjs` (or the equivalent) does not export.
     - `@covers FR-xxx` ids that do not exist in spec.md. gates.mjs runs a file only once ALL its FRs are delivered, so an unknown FR defers the file forever and the phase passes without it. Map it to the real FR.
     - Test files whose `@covers` mixes early and late FRs: they run only from the latest of those phases. Confirm that matches the plan.
     - Load or memory success criteria ("a full sweep at limit N with K concurrent requests does not restart the service") that are tested on only a small sample. A sampled test passes while production still crashes. The test must run the FULL sweep twice against its own spawned server with the production limits (e.g. `node --max-old-space-size=256 server/index.js` on a free port), and assert the process is still alive afterwards.
5. **Implement each phase (Gemini, separate process).** `terminal(command="bash scripts/sdd/run_phase.sh specs/NNN-x <phase>", background=true, notify=true)`; last phase adds `--final`. Exit 0 = PASS, 3 = ESCALATE. Spec Kit `.specify/extensions.yml` hooks run automatically (`hooks.mjs`); with `"parallel": true` consecutive `[P]` tasks run as concurrent Gemini sessions. Runs in an isolated worktree `.sdd/worktrees/NNN-phaseN`; gates serve the app from the worktree (`serve`/`servePort`, tests read `SDD_BASE_URL`). Merge branch `sdd/NNN-phaseN` into base before the next phase. Read ONLY the exit code and `specs/NNN-x/.sdd/phaseN.verdict.json`.
6. **Escalation (Opus, only then).** Read `phaseN.verdict.json`, `phaseN.feedback.md`, `phaseN.review.md` (the diff only for `highRisk` paths). Fix spec/contracts, split the task, or ask the founder. Re-run step 5. Triage playbook:
   - Sort each failed gate into one of three causes: **infra** (test helper, gate config, missing dir), **implementer scope creep**, or **real defect**. Acceptance output that prints every suite PASS and then crashes in teardown is infra, not product.
   - Fix infra and over-specified tests on the base branch and commit there. Then `git merge <base>` inside `.sdd/worktrees/NNN-phaseN`. The re-run reuses the existing branch and worktree, so the previous attempt's code is kept.
   - Put instructions for the re-run into the phase's section of `tasks.md` as an "Architect note" (commit on base, merge into the worktree). Do NOT put them in `phaseN.feedback.md`: `run_phase.sh` deletes that file at start, and only the tasks.md phase section reaches the new prompt.
   - Name the exact revert (file + line) for scope creep. Run `verify_specs --pre-tests` after editing tasks.md, then re-run the phase.
   - Long reviewer runs: a full multi-file diff review by Gemini can run 5–8 minutes. Poll `run_phase.log` and wait for the verdict before assuming a stall; do not kill or duplicate running reviewer processes.
   - Mid-turn user steering and background yield: if an out-of-band user message interrupts a foreground terminal command, the runtime moves it to background (`yielded_to_background`). Track and wait on it via `process_manage(action='poll'|'wait', session_id=...)` before taking conflicting actions.
   - **A gate that fails intermittently (one attempt red, the next green) is not evidence against the phase.** Before writing an Architect note, run the failing test on N≥6 fresh cold starts of BOTH the base commit (a throwaway `git worktree add <scratch> <base-sha>` with `node_modules` symlinked) and the phase worktree. If base also fails, the defect is pre-existing: give it its own FR, a deterministic locked test and its own phase, and re-run the current phase's gates alone. Put debug logging only in a scratch copy, never in the worktree, so the scope fence and diff stay clean. Find the cause by logging the upstream's last message before each disconnect (close code, pending request count): the upstream's own error frame usually names it.
   - If the escalation was only a locked-test defect and the worktree code already passed every other gate, run the gates alone first. Command: `cd .sdd/worktrees/NNN-phaseN && node /path/to/repo/scripts/sdd/gates.mjs specs/NNN-x <phase> <attempt> [--final]` in the background. This costs zero tokens and avoids a fresh three-attempt implementer loop. A gates-only PASS is NOT mergeable: the base `phaseN.verdict.json` still holds the failed attempt, and `merge_phase.sh` then prints `MERGED` while merging nothing. Re-run `run_phase.sh` to get the official verdict and reviewer pass, and after every `merge_phase.sh` confirm that the phase's tasks flipped to `[x]` and `git log` shows the merge before you build or deploy.
7. **Ship.** Merge, deploy with the project's command, report to the founder with verdict files as evidence (Persian text + full voice note).
   - **Merge conflicts.** `merge_phase.sh` printing `MERGE FAIL: conflicts` can leave conflict markers behind. Never chain `git commit -a` or the next `run_phase.sh` after it in the same command. Check `git diff --name-only --diff-filter=U` and `grep -rn '^<<<<<<< '` first. Conflicts come from architect edits to tasks.md on base while a phase runs, so append new phases only after merging the running one.
   - **Never lock a later phase's test before that phase exists in tasks.md.** gates.mjs treats the last phase in tasks.md as final, and `--final` runs every locked file. A test locked early therefore runs inside the current phase, whose scope fence forbids the files it needs, and the implementer escalates with a correct SPEC_PROBLEM. If you write the next FR and test early, either append that phase's tasks in the same commit (accepting a tasks.md merge into the running worktree), or keep the test unlocked and uncommitted until the running phase merges. Once later phases are listed, run every phase except the last WITHOUT `--final`, so each runs only the tests whose FRs it has delivered. An urgent fix found mid-plan can take the next phase number: renumber the already-specced later phase in tasks.md before locking.
   - **Post-deploy audit (mandatory for audit-driven specs).** Re-run the spec's original black-box audit against production right after deploy, at the same concurrency, and check the service restart counter (`systemctl show <svc> -p NRestarts`) and `journalctl` for `heap out of memory`. Green gates do not prove production survives full-scale load. Audit what the USER can reach, not only the fixed catalogue: the top search results for common queries, and random browsed items at deep offsets. Report the result only after the audit finishes. Verify scheduled behaviour (an hourly idle refresh, a nightly re-fetch) only after its interval has elapsed. Compute the next due time from the persisted `fetchedAt` and re-check after it, instead of reading an un-refreshed value right after restart as a failed deploy.
   - **Red-checking a test that SPAWNS other test files is itself a production run.** Before the first red run, sandbox every child: preload `NODE_OPTIONS=--require <helper>` that exits on any socket to the production port (patch `net.Socket.prototype.connect` AND subscribe to `undici:client:beforeConnect` for `fetch`), and verify the block with a one-line fetch first. Snapshot production state (user total, settings `updatedAt`, audit line count) before and after. If leftovers appear, diff against the last `cp -a` review copy and remove only the new records through the admin API (deletes may need a `confirm` body).
- **Also audit production for state left behind by tests:** platform announcements or banners, maintenance flags, test users and settings. Any acceptance file whose base URL defaults to the production port mutates production when it is run without `SDD_BASE_URL`. Clear leftovers through the admin API, never by editing data files. Make such tests spawn their own server or refuse to run without an explicit base URL.
   - **If the audit fails:**
     1. Roll back at once: `git checkout <last-good-sha> -- <src dirs>`, run the build, restart, and verify the service answers. Then `git checkout HEAD -- <src dirs>` to restore the tree.
     2. Reproduce the failure offline. Run the suspect module directly in node and measure heap per request, or start a second instance on a spare port.
     3. Write a reproducing acceptance file (`@spec NNN`, `@covers FR-x`) and run it to confirm it fails before freezing it with `lock_tests.mjs`.
     4. Append a "Converge" phase to tasks.md with an Architect note naming the root cause and the files involved. Commit on base and run it with `--final`.
     5. Report the founder the rollback honestly. Never call the work done until the production audit passes.

**Language:** every message the founder sees is Persian, including the one-line progress notes written between tool calls. An English interim line reads as "you answered in English".

**Reporting cadence (founder preference):** after every pipeline milestone (spec gate PASS, `AUTHOR OK`, each phase verdict, deploy), send a short Persian status: what passed (the gate names), what changed for the user, what runs next. Make it clear which model did which part (Opus = spec/test/review/merge, Gemini = implementation). The founder checks that Gemini carries the implementation load and Opus does not do everything. Hermes `/voice all` already voices the full reply text, so do NOT attach a separate `speak-fa-long.sh` file: it duplicates the audio. Kick off the next background step BEFORE writing the report so the pipeline never idles while you write.

**Architect converge loop (fast path, used after a review finds defects in merged-but-undeployed code):**
1. Write the FR on base with each defect as a lettered, machine-checkable clause (observed defect + required behaviour).
2. Opus writes the reproducing locked test directly. Spawn its own server with production heap limits on a random port, plus a local mock of the upstream built from real keyless fixtures. The mock injects slow, 5xx and non-JSON answers.
3. Red-check it against the current code. It must fail on every defect, and each failure message must name that defect, not a test bug. A "setup" assertion that reports the mock served nothing usually means the injected mock route sits below an earlier route that already answers the same path; put override routes first in the handler. For example, a check that compares a clock widget's full text compares the ticking time, not the zone label. Fix assertions that fail for the wrong reason before freezing, because a locked wrong assertion forces an escalation later. Then `lock_tests.mjs freeze`, `verify_specs --pre-tests`, and commit spec + tasks + lock + test together.
4. Append a Converge phase with an Architect note giving the root cause per defect (file + mechanism) and "do NOT touch" boundaries. Then run `run_phase.sh … <N> --final` in the background with notify. Opus waits idle and does not investigate further.
5. On PASS, do the architect review (below), then `merge_phase.sh`, deploy, and run the production audit.

**Architect review before merge (mandatory, even on 9/9 PASS):**
- In the worktree, run `git diff <spec-commit> HEAD -- server client` and grep the added lines for test-fixture names, mock ports, `NODE_ENV`/`SDD_` branching and non-ASCII literals in files that must use i18n.
- Start the worktree server on a spare port with the REAL env and secrets, using a FRESH data dir in scratch. To reproduce production's stale state, copy production's data dir with `cp -a` (it preserves mtimes): `cp -r` stamps every file as fresh, so freshness/refresh logic that reads mtime skips the refresh and looks broken. Before querying, confirm by PID (`ss -ltnp | grep <port>`) that the listener is the process you just started. A leftover review server from an earlier attempt can answer on the same port and replay stale results.
- Compare field by field against the official source over ≥ 3 unrelated records/instruments, not just the fixture one: the fixture's IDs and shapes are the ones the test already covers. Include some old/large and some random ones. Over each record's full history, a sample of ≥ 30 rows is the minimum.
- Before calling a gap a mismatch, page through the API's per-request cap (e.g. `limit` max 5000, then `to_time=<oldest>-1`). Count catalogues with the browse endpoint's `total`, not a capped search list. A capped response looks like missing data.
- Check which source actually served the data (the response `source` field and the files written to the data dir), not what a status endpoint claims. A status endpoint can report the new primary while every answer still comes from the fallback.
- Watch for numeric IDs above 2^53 in upstream JSON (`JSON.parse` silently rounds them). Keys used for later upstream calls must come from a source that delivers them as strings.
- Recompute derived values yourself from the official raw inputs, not from the API under review. For example, rebuild back-adjusted prices from the official adjustment-event list (cumulative factor `pClosing/pClosingNotAdjusted` for every event after the bar), and compare raw and derived values on every row.
- **Before calling a catalogue count a mismatch, sample the official source ≥ 5 times over a minute** and compare the union and intersection. Some official endpoints return a varying subset on each call. That is an upstream property that needs its own retention FR, not a defect of the phase.
- **UI phases: review in a real browser at desktop (1440 and 1280) AND mobile (390) with real data.** Use the repo's own harness (`tests/qa_lib.cjs` `launch('mobile'|'desktop')`) and reach every new control through the real user path (mobile bar drawers, «+ پنل‌ها» menus), not only through `window.__APP__` calls. Count an element as visible only if no ancestor is `display:none`: a control inside a header group that is hidden on mobile reports `offsetParent` and a non-empty `innerText` while being 0×0. Take screenshots and check them for wrapped labels, `$` or Latin leftovers on rial instruments, and synthetic numbers next to official ones.
- Run the same probe against production too, so findings split into regressions (block the merge) and pre-existing gaps the phase already improves. Merge the improvement and turn the pre-existing gaps into the next FR with a locked browser test, red-checked on current code.
- When the defect lives in output produced by a vendored dependency (a chart library's legend or clock reading what the app passes in), the Architect note must locate the app-side call site and state "do not edit node_modules". Gemini otherwise patches the vendor bundle, and that patch is lost on the next install.
- Record accepted design debt (e.g. a process-wide monkey-patch the gates cannot see) as an "Architect review of phase N (merged)" note in tasks.md above the next phase, with an explicit "next phases must not extend it" constraint.
- **Poll the primary-source status during the review, not only at its start.** If a server flips to its fallback while the real upstream answers health probes, wrap the failure counter (e.g. `recordRelayFailure`) in a scratch copy and log each error plus the caller's stack line (`new Error().stack.split('\n')[2]`). Often one endpoint returns sporadic 5xx while health stays green. The FR then has to say that failover counts only transport and health-probe failures, and a per-endpoint 5xx retries or fails only that request: a shared consecutive-failure counter turns one flaky endpoint into a full source switch. **Classify by HTTP status first, never by body shape.** The same upstream sends 5xx with an empty body at one time and with an nginx HTML error page (labelled `application/json`) at another. A classifier that counts "HTML body = proxy broken" still flips over on the second form. Rule: any 5xx is upstream (retry with backoff, fail only that request); HTML or non-JSON counts toward failover only on a 200. In the mock, inject every body variant you have observed live.
- **A new caching/de-dup FR can break older locked tests that inject consecutive upstream faults back-to-back.** Before locking it, grep the locked tests that count mock-served faults (`served < N`) and add a wait longer than the new cache TTL between injections in the same commit. Otherwise the implementer escalates with a correct "mutually exclusive" SPEC_PROBLEM after three attempts.
- **Review time-dependent upstreams in every market state you can reach:** in session, pre-session and closed day. Many official endpoints answer EMPTY outside the session (today's trades, today's client-type totals), and the client must not treat an empty timeframe as a removed symbol. When the review runs outside the session, check what the user sees on intraday timeframes and the live panels. Look for a dated history endpoint for the last session as the fallback, and require the answer to be marked stale with its session date.
- **Before reporting a UI defect, confirm the probe actually reached the control.** A click on a selector that does not exist does nothing silently, and the next assertion then "proves" a defect. Assert the element exists, and drive the control the user really uses (e.g. the bottom-bar time-zone menu, not a guessed button id). Likewise, before reporting "wrong label shown", check the element's computed `display`: `innerText` of a container still includes children hidden with an inline `display:none` in some layouts, so a regex over the panel text matches a badge the user cannot see.
- **Reproduce intermittent upstream faults on demand with an A/B fault-injection proxy** instead of waiting for the upstream to misbehave during the review. Put `scripts/flaky_upstream_proxy.cjs` in front of the REAL upstream. It injects the exact live-observed error body on a matching path at a fixed rate. Start the phase worktree server and a base-code server side by side, both pointed at the proxy (keep the secret path prefix), and run the same sweep on both. Mergeable result: the phase server answers every request with the primary source kept and zero failover count, while the base server reproduces the production defect. Kill the proxy and both servers by PID afterwards.
- **After deploying a source-handling phase, load production with a broad sweep (≈ 50 random catalogue instruments on the affected endpoints, sequential) during live market hours, and poll the primary-source status after it.** Single-symbol checks pass while concurrent large upstream payloads expose failover and retry defects only under load.
- **Phases that change request or socket plumbing** (request-context middleware, upstream connection or session limits) need ≥ 10 cold starts against the REAL upstream before merge, running the broadest locked API test and counting upstream protocol errors in each server log. The mock-based gates cannot see real upstream rate limits.
- Kill the review server by PID afterwards. Merge only at zero data mismatches.
- **Review found a defect the gates missed:** first make the locked test reproduce it. Usually the mock was friendlier than production, so mirror the real deployment shape in the mock (URL path prefix, HTML at the host root, real timings). Prove the amended test is red on the phase code: copy it and point its ROOT at the worktree. Then on base: fix the FR clause, add an "Architect note (re-run …)" with file + mechanism above the phase tasks, flip those tasks back to `[ ]`, freeze, and commit. Run `git merge <base>` in the worktree, and resolve the expected tasks.md conflict with `git checkout --theirs <tasks.md>`, because base carries the note and the open tasks. Then re-run `run_phase.sh … --final`.

**Time-dependent logic needs a test clock in the FR.** Any trading-day, market-hours or quota-day rule must read one clock function overridable by an env var (e.g. `TC_TSE_NOW`, ISO instant + elapsed). Otherwise the locked test can only pass on the weekday it was written, and wrong-date defects stay invisible.

**Deploy from `main` when the base is a work branch:** QA runs leave modified tracked result files that block `git checkout main`. `git stash push -- <those files>`, checkout main, merge base, build, restart, then go back to base and `git stash pop`. Append new secrets to the service env file only from `/root/.secrets/*` (`echo "K=$(cat file)" >>`, chmod 600) and never print them. After the restart, confirm the key appears in neither journalctl nor the API responses.

**Cite FRs in tasks.md in plain `(FR-028)` form.** verify_specs matches `\bFR-\d{3}\b`, so a lettered
clause such as `(FR-028a)` counts as "tasks without FR reference" and the spec gate goes red. Put the clause
letters in the spec and the task text, and keep the parenthesised reference plain.

**Tasks that delete files:** after merging a phase whose done (`[x]`) task deleted a file the task text cites, `verify_specs` fails ("tasks cite missing paths") and the next phase starts on a red spec. Run `verify_specs --pre-tests` right after every merge, reword the done task so it no longer names the deleted path, and commit before starting the next phase.

**Restarting a phase that started on a wrong base:** kill the background `run_phase.sh` by its process session, then `git worktree remove --force .sdd/worktrees/NNN-phaseN && git branch -D sdd/NNN-phaseN` before re-running. Otherwise run_phase reuses the stale branch.

**Architect spot-check after a PASS (zero diff reading):** merge, then grep the merged tree for the review-checklist's forbidden patterns (e.g. a removed generator name, `Math.random` in a deterministic path). If a pattern is still present because a later phase owns its removal, confirm that the later phase's tasks name it.

## Retrofit procedure
For an existing product without specs, follow `references/retrofit.md` (areas.tsv → recon.sh → spec.md per area → retrofit.sh → Converge phase).

## Pitfalls
- **Mock upstreams must match the production deployment shape and quirks, not just the payload.** Mirror:
  - the base URL exactly as configured, with any secret path prefix kept verbatim, and what the host answers outside that path (an HTML page);
  - the auth header;
  - the real response sizes and latency;
  - data quirks the code can break on, such as large numeric IDs that round, or empty lists for unknown keys;
  - non-JSON bodies served as `application/json` (e.g. a health/time endpoint returning a bare date string). A mock that returns valid JSON hides a probe that can never succeed in production, so the service never returns to the primary after an outage;
  - an outage-then-recovery step (the mock answers 502 for a while, then recovers), with an assertion that the service returns to the primary within the probe interval.

  A mock served at `/` hides an implementation that rewrites the URL path, so the phase passes every gate and never reaches the real upstream. When a review finds such a gap, add the quirk to the mock, red-check the amended test on the phase code, then re-run with an Architect note.
- **Keep the chat model from switching silently.** Limit Hermes `fallback_providers` to the SAME architect model through a backup router (a router outage then keeps Opus; an account rate limit stops the work instead of switching). Run a cron notifier that tails `~/.hermes/logs/agent.log*` for `Fallback activated:` / `Primary runtime restored` and messages the founder on Telegram. Change it with `hermes config set fallback_providers '<json>'`, never by rewriting config.yaml with a YAML dump.
- **Architect identity check.** If the chat model silently falls back (Hermes `fallback_providers`, `gateway_runtime.fallback_active` in state.db `sessions.model_config`; tool-call ids `call_…` instead of `toolu_…`), the conversation is no longer Opus. Stop ALL architect duties: no merges, no spec edits, no verdict trust. Tell the founder at once. Afterwards audit that window: `session_model_usage` gives the time range, and `messages.tool_calls` gives every command run. Gemini once merged a phase after reading only `review.md` and `--stat`, and also called itself Opus in a founder report.
- **A green phase is not an architect review.** Gates only prove what the locked test asserts. A phase can pass all of them while dating data by the server's calendar (fabricating bars on closed days) or swallowing upstream failures (`catch(_){}` leaving a sticky queued flag). Always do the real-data review above before merging.
- Before trusting an earlier security/probe result, re-read the code's actual parameter names. A probe with the wrong query key gets a generic 400/200 and looks like a broken allow-list.
